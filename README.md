## Overview

This repository manages Azure infrastructure using Terraform. The pipeline supports two backend modes:

- **Terraform Cloud** (`cloud`) — remote state and plan execution via Terraform Cloud
- **Local** (`local`) — state committed directly to the repository, CLI-driven applies via GitHub Actions

The active backend is controlled by the `TF_DEFAULT_BACKEND` repository variable. Setting it to `local` enables the local CLI workflow; any other value (or leaving it unset) defaults to Terraform Cloud.

## Branching Strategy

Each environment has a **dedicated long-lived branch**. Environments are fully independent — you cannot merge between environment branches directly.

### Environment Branches

| Branch | Environment | Purpose |
|--------|-------------|---------|
| `dev`  | Development | Active development and feature integration |
| `test` | Test/Staging | Pre-production validation |
| `main` | Production  | Live infrastructure |

### Feature Branch Naming

All work is done on short-lived feature branches that merge into the appropriate environment branch.

```
<type>/<description>-<env>
```

| Suffix | Target Branch | Example |
|--------|--------------|---------|
| `-dev`  | `dev`  | `feat/add-key-vault-dev` |
| `-test` | `test` | `fix/kv-policy-test` |
| `-prod` | `main` | `chore/update-providers-prod` |

The CI workflow enforces this — a branch ending in `-dev` **must** target `dev`. Targeting any other branch will fail the pipeline.

### Branch Type Prefixes

| Prefix | Usage |
|--------|-------|
| `feat/` | New infrastructure resources or modules |
| `fix/` | Bug fixes to existing configuration |
| `chore/` | Dependency updates, provider version bumps |
| `docs/` | Documentation-only changes |
| `refactor/` | Restructuring with no functional change |

### Merge Rules

The following merges are **blocked by the pipeline**:

| ❌ Not Allowed | Reason |
|----------------|--------|
| `dev` → `test` | Environments are independent |
| `dev` → `main` | Environments are independent |
| `test` → `main` | Environments are independent |
| `test` → `dev`  | Environments are independent |
| `main` → `dev`  | Environments are independent |
| `main` → `test` | Environments are independent |

Each environment is managed separately. Changes to `test` or `main` are made directly via a feature branch targeting that environment — not by promoting from a lower environment.

## Naming Standards

### Terraform Resources

All resources follow a consistent naming convention:

```
<prefix>-<project>-<resource_type>-<env>-<instance>
```

**Example:** `nr-fabric-kv-dev-01`

| Field | Description | Example |
|-------|-------------|---------|
| `prefix` | Organization/team shortcode | `nr` |
| `project` | Project or workload name | `fabric` |
| `resource_type` | Azure resource abbreviation | `kv`, `rg`, `vnet` |
| `env` | Environment name | `dev`, `test`, `prod` |
| `instance` | Zero-padded instance number | `01`, `02` |

### Module Inputs

Use the standard module input fields consistently across all module calls:

```hcl
module "example" {
  source          = "../modules/azure/<service>"

  prefix          = "nr"
  suffix          = "tools"
  project         = "fabric"
  env             = var.ENVIRONMENT     # always use var.ENVIRONMENT — never hardcode
  Instance_Number = "01"
  location        = "canadacentral"
}
```

> **Important:** Never hardcode `env = "dev"`. Always use `env = var.ENVIRONMENT` so the value is injected by the CI/CD pipeline at plan and apply time.

### Variable Names

- Use `UPPER_SNAKE_CASE` for variables passed via `TF_VAR_*` environment variables (ARM credentials, environment)
- Use `lower_snake_case` for all other Terraform variables and locals

### File Names

| File | Purpose |
|------|---------|
| `main.tf` | Primary resource declarations |
| `variables.tf` | Input variable declarations |
| `outputs.tf` | Output value declarations |
| `locals.tf` | Local value computations |
| `providers_cloud.tf.tpl` | Terraform Cloud backend provider template |
| `providers_local.tf.tpl` | Local backend provider template |
| `README.md` | Auto-generated module documentation |

## Environment Configuration

### How Environment is Injected

The environment value flows through the pipeline as follows:

```
Branch name (dev / test / main)
  → TF_ENV (set by CI/CD from base_ref)
    → TF_VAR_ENVIRONMENT (set as process environment variable on plan/apply step)
      → var.ENVIRONMENT in Terraform
        → env = var.ENVIRONMENT in module calls
```

Credentials follow the same path — GitHub secrets are mapped to `TF_VAR_*` environment variables scoped only to the plan or apply step. No file is ever written to disk containing secret values.

### `variables.tf` — Required Declaration

Every artifact entrypoint must declare the following variables:

```hcl
variable "ENVIRONMENT" {
  description = "Deployment environment (dev, test, prod)"
  type        = string
}

variable "ARM_SUBSCRIPTION_ID" {
  description = "Azure Subscription ID"
  type        = string
  sensitive   = true
}

variable "ARM_TENANT_ID" {
  description = "Azure Tenant ID"
  type        = string
  sensitive   = true
}

variable "ARM_CLIENT_ID" {
  description = "Azure Service Principal Client ID"
  type        = string
  sensitive   = true
}

variable "ARM_CLIENT_SECRET" {
  description = "Azure Service Principal Client Secret"
  type        = string
  sensitive   = true
}
```

### `TF_VAR_*` — How Variables Are Passed in the Pipeline

Terraform automatically maps any environment variable named `TF_VAR_<NAME>` to the corresponding input variable `var.<NAME>`. The pipeline sets these directly on the plan and apply steps rather than writing a credentials file to disk:

```yaml
env:
  TF_VAR_ARM_SUBSCRIPTION_ID: ${{ vars.ARM_SUBSCRIPTION_ID }}
  TF_VAR_ARM_TENANT_ID:       ${{ secrets.ARM_TENANT_ID }}
  TF_VAR_ARM_CLIENT_ID:       ${{ secrets.ARM_CLIENT_ID }}
  TF_VAR_ARM_CLIENT_SECRET:   ${{ secrets.ARM_CLIENT_SECRET }}
  TF_VAR_ENVIRONMENT:         ${{ env.TF_ENV }}
```

Values only exist in the process environment for the duration of that single step. GitHub Actions masks all secret references in logs automatically. No `*.tfvars` file is generated or cleaned up.

## Backend Configuration

### Switching Backends

Set the `TF_DEFAULT_BACKEND` repository variable in GitHub:

| Value | Behaviour |
|-------|-----------|
| `cloud` (default) | Uses Terraform Cloud for remote state and plan execution |
| `local` | Uses local backend; state committed to repo; apply runs via GitHub Actions |

### Local Backend State

When using the local backend, `terraform.tfstate` lives at `build/artifacts/terraform.tfstate` and is committed to the repository after every successful apply by the CD workflow.

Ensure your `.gitignore` does **not** exclude state files in this path:

```gitignore
# Allow state files for local backend
!build/artifacts/terraform.tfstate
!build/artifacts/terraform.tfstate.backup
```

> **Note:** The state file may contain sensitive output values. Ensure your repository has appropriate access controls and that sensitive outputs are marked `sensitive = true` in Terraform.

### Terraform Cloud Backend

The cloud backend uses a remote workspace per environment. The workspace name is defined in `providers_cloud.tf.tpl`.

```hcl
terraform {
  backend "remote" {
    organization = "bcgov-tfc"
    workspaces {
      name = "nr-dap-fabric-ci-dev"
    }
  }
}
```

## CI/CD Pipeline

### CI — Pull Request Checks (`ci.yml`)

Triggered on every pull request targeting `dev`, `test`, or `main` when Terraform files change.

```
PR Opened / Updated
  │
  ├─► [Job 1] Validate Branch Strategy
  │     └─ Enforce merge rules and branch naming conventions
  │
  ├─► [Job 2] Resolve Environment & Backend
  │     └─ Derive env_name (dev/test/prod) and backend (cloud/local)
  │
  └─► [Job 3] Terraform Quality Checks
        ├─ Select providers file (cloud or local template)
        ├─ terraform fmt -recursive         → auto-formats and commits if needed
        ├─ tflint                           → linting (errors only)
        ├─ terraform init (artifacts)
        ├─ terraform init -backend=false (modules)
        ├─ terraform validate (artifacts + modules)
        ├─ Generate ci.auto.tfvars          → injects ENVIRONMENT + ARM credentials
        ├─ terraform plan
        ├─ terraform-docs                   → auto-updates README.md files
        └─ Cleanup generated files
```

Auto-commits made by the pipeline are tagged `[skip ci]` to prevent re-triggering.

### CD — Post-Merge Apply (`cd.yml`)

Triggered when a PR is **merged** into `dev`, `test`, or `main`. Only runs when `TF_DEFAULT_BACKEND` is set to `local` — when using Terraform Cloud, applies are managed remotely and this job is skipped entirely.

```
PR Merged (local backend only)
  │
  ├─ Checkout merged branch
  ├─ Select providers_local.tf.tpl
  ├─ Generate ci.auto.tfvars
  ├─ terraform init
  ├─ terraform apply -auto-approve
  ├─ Commit terraform.tfstate back to branch
  └─ Comment on PR with apply result
```

### GitHub Repository Variables & Secrets

#### Variables (`vars.*`)

| Variable | Description |
|----------|-------------|
| `TF_DEFAULT_BACKEND` | Set to `local` to enable local backend; omit or set to `cloud` for Terraform Cloud |
| `TF_VERSION` | Terraform version override (defaults to `1.9.0`) |
| `ARM_SUBSCRIPTION_ID` | Azure Subscription ID (per environment) |

#### Secrets (`secrets.*`)

| Secret | Description |
|--------|-------------|
| `ARM_CLIENT_ID` | Azure Service Principal Client ID |
| `ARM_CLIENT_SECRET` | Azure Service Principal Client Secret |
| `ARM_TENANT_ID` | Azure Tenant ID |
| `TF_CLOUD_TOKEN` | Terraform Cloud API token (cloud backend only) |

Variables and secrets are scoped per **GitHub Environment** (`dev`, `test`, `prod`), allowing different credentials per environment.

### Setting Up GitHub Environments, Variables, and Secrets

#### Step 1 — Create the GitHub Environments

Each environment (`dev`, `test`, `prod`) must be created in GitHub before secrets can be scoped to it.

1. Go to your repository on GitHub
2. Click **Settings** → **Environments** (left sidebar)
3. Click **New environment**
4. Create three environments, one at a time: `dev`, `test`, `prod`
5. For `prod`, consider enabling **Required reviewers** — add one or more team members who must approve before a production apply can proceed

#### Step 2 — Add Repository-Level Variables

These variables apply across all environments and control pipeline behaviour.

1. Go to **Settings** → **Secrets and variables** → **Actions**
2. Click the **Variables** tab
3. Click **New repository variable** and add:

| Name | Value | Notes |
|------|-------|-------|
| `TF_DEFAULT_BACKEND` | `local` or `cloud` | Controls which backend the pipeline uses |
| `TF_VERSION` | `1.9.0` | Override Terraform version if needed |

#### Step 3 — Add Environment-Scoped Variables and Secrets

Credentials are scoped **per environment** so that `dev`, `test`, and `prod` each use their own Azure Service Principal. Repeat the steps below for each of the three environments.

1. Go to **Settings** → **Environments**
2. Click the environment name (e.g. `dev`)
3. Under **Environment variables**, click **Add variable** and add:

| Name | Value |
|------|-------|
| `ARM_SUBSCRIPTION_ID` | The Azure Subscription ID for this environment |

4. Under **Environment secrets**, click **Add secret** and add:

| Name | Value |
|------|-------|
| `ARM_CLIENT_ID` | Service Principal Application (Client) ID |
| `ARM_CLIENT_SECRET` | Service Principal Client Secret |
| `ARM_TENANT_ID` | Azure Active Directory Tenant ID |
| `TF_CLOUD_TOKEN` | Terraform Cloud API token (cloud backend only — can be left blank for local) |

> **Why environment-scoped?** Scoping secrets to an environment means the `dev` pipeline job can only access `dev` credentials, and the `prod` job can only access `prod` credentials. A misconfigured branch cannot accidentally apply against production.

#### Step 4 — Finding Your Azure Service Principal Values

If you need to create a new Service Principal or find existing values, use the Azure CLI:

```bash
# Login
az login

# Create a new Service Principal with Contributor role on a subscription
az ad sp create-for-rbac \
  --name "sp-terraform-dev" \
  --role Contributor \
  --scopes /subscriptions/<subscription-id> \
  --sdk-auth

# The output contains all four values you need:
# {
#   "clientId":       "→ ARM_CLIENT_ID",
#   "clientSecret":   "→ ARM_CLIENT_SECRET",
#   "subscriptionId": "→ ARM_SUBSCRIPTION_ID",
#   "tenantId":       "→ ARM_TENANT_ID"
# }
```

```bash
# To find an existing Service Principal's values
az account show --query id -o tsv                          # Subscription ID
az account show --query tenantId -o tsv                    # Tenant ID
az ad sp list --display-name "sp-terraform-dev" --query "[].appId" -o tsv  # Client ID
```

> Create a **separate Service Principal per environment** with access only to that environment's subscription or resource group. Never share a single Service Principal across environments.

## Local Development

### Prerequisites

- [Terraform](https://developer.hashicorp.com/terraform/downloads) >= 1.9.0
- [TFLint](https://github.com/terraform-linters/tflint) v0.50.3
- [terraform-docs](https://terraform-docs.io) v0.17.0
- Azure CLI or a Service Principal with access to your dev subscription

### Passing Credentials Locally

When running Terraform from your desktop you need to supply the same variables the pipeline injects via `TF_VAR_*`. The cleanest approach is to export them as environment variables in your shell session — no file containing secrets is written to disk or risks being accidentally committed.

**macOS / Linux (bash or zsh):**

```bash
export TF_VAR_ARM_SUBSCRIPTION_ID="xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
export TF_VAR_ARM_TENANT_ID="xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
export TF_VAR_ARM_CLIENT_ID="xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
export TF_VAR_ARM_CLIENT_SECRET="your-client-secret-value"
export TF_VAR_ENVIRONMENT="dev"
```

**Windows (PowerShell):**

```powershell
$env:TF_VAR_ARM_SUBSCRIPTION_ID="xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
$env:TF_VAR_ARM_TENANT_ID="xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
$env:TF_VAR_ARM_CLIENT_ID="xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
$env:TF_VAR_ARM_CLIENT_SECRET="your-client-secret-value"
$env:TF_VAR_ENVIRONMENT="dev"
```

These variables exist only for the duration of the shell session and are never written to disk. Terraform picks them up automatically when you run `plan` or `apply`.

To avoid re-exporting on every session, you can store them in a file that is **never inside the repository**:

```bash
# ~/.config/terraform/dev.env  ← outside the repo entirely
export TF_VAR_ARM_SUBSCRIPTION_ID="xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
export TF_VAR_ARM_TENANT_ID="xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
export TF_VAR_ARM_CLIENT_ID="xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
export TF_VAR_ARM_CLIENT_SECRET="your-client-secret-value"
export TF_VAR_ENVIRONMENT="dev"
```

Then source it when needed:

```bash
source ~/.config/terraform/dev.env
```

> Never place this file anywhere inside the cloned repository directory. Store it in your home directory or a path that cannot be accidentally staged by git.

### Setup

```bash
# 1. Copy the local provider template
cd build/artifacts
cp providers_local.tf.tpl providers.tf

# 2. Export your credentials for the session (see above)
source ~/.config/terraform/dev.env

# 3. Initialise
terraform init

# 4. Plan — Terraform reads TF_VAR_* from the environment automatically
terraform plan

# 5. Apply
terraform apply
```

### Switching Environments Locally

To target a different environment, source a different credentials file or re-export `TF_VAR_ENVIRONMENT` and the corresponding ARM values for that environment:

```bash
source ~/.config/terraform/test.env
terraform plan
```

> **Do not run `terraform apply` locally against `test` or `prod`** without team awareness. Raise a PR and let the CD pipeline handle applies to those environments to maintain a clear audit trail.

### Formatting

Always format before committing. The CI pipeline will auto-format and commit if you forget, but it's best practice to do it locally:

```bash
terraform fmt -recursive
```

### Generating Documentation

Documentation is auto-generated by the CI pipeline, but you can also run it locally:

```bash
terraform-docs markdown table --output-file README.md --output-mode inject ./build/modules/azure/<module>
```

## Code of Conduct

### Our Standards

All contributors are expected to:

- Write clear, well-commented Terraform code
- Follow the naming and branching conventions defined in this document
- Review PRs constructively and promptly
- Keep sensitive values out of committed code — use variables and secrets
- Not merge your own PR without at least one approval (except hotfixes in emergencies, documented in the PR)

### What is Not Acceptable

- Committing credentials, tokens, or subscription IDs directly in `.tf` or `.tfvars` files
- Force-pushing to `dev`, `test`, or `main`
- Bypassing CI checks by adding `[skip ci]` to feature branch commits
- Making manual changes to Azure resources that are managed by this repository without creating a corresponding Terraform change

### State File Integrity (Local Backend)

When using the local backend:

- Never manually edit `terraform.tfstate`
- Never delete `terraform.tfstate` without team consensus and a documented migration plan
- If a state conflict occurs, raise a GitHub Issue immediately before attempting resolution

## Contributing

### Opening a Pull Request

1. Create a feature branch from the target environment branch following the [naming standard](#feature-branch-naming)
2. Make your changes
3. Run `terraform fmt -recursive` and `tflint --recursive` locally
4. Open a PR targeting the correct environment branch
5. Ensure all CI checks pass
6. Request review from at least one team member
7. Do not merge until approved

### PR Description Template

```markdown
## Summary
Brief description of what this change does.

## Resources Affected
- List the Terraform resources being added, modified, or destroyed

## Environment
- [ ] dev
- [ ] test
- [ ] prod

## Testing
Describe how this was validated (plan output, manual verification, etc.)

## Related Issues
Closes #<issue-number>
```

### Commit Message Convention

Follow [Conventional Commits](https://www.conventionalcommits.org/):

```
<type>: <short description>

[optional body]

[optional footer: Closes #123]
```

| Type | Usage |
|------|-------|
| `feat` | New resource or module |
| `fix` | Bug fix |
| `chore` | Provider/version bumps, maintenance |
| `docs` | Documentation only |
| `refactor` | Code restructure, no functional change |
| `revert` | Reverts a previous commit |

Auto-commits from the pipeline use `fmt:`, `docs:`, and `state:` prefixes.

## Communication & Issues

All team communication related to infrastructure changes is tracked via **GitHub Issues**.

### Issue Labels

| Label | Usage |
|-------|-------|
| `bug` | Something is broken or behaving unexpectedly |
| `enhancement` | New resource or capability request |
| `question` | General question or clarification needed |
| `state-conflict` | State file conflict requiring team resolution |
| `security` | Credential exposure or access control concern |
| `blocked` | Work blocked pending external dependency |

### Opening an Issue

Use GitHub Issues for:

- Reporting a failed pipeline that cannot be resolved by the author
- Proposing new modules or significant architectural changes before implementing them
- Documenting a manual Azure change that needs to be reconciled in Terraform
- Raising a state conflict (local backend)
- Security concerns (use the `security` label and keep details vague in public — use a private note or direct message for sensitive details)

### Issue Template

```markdown
## Description
What happened or what is being requested.

## Environment
- Branch/Environment: dev / test / prod
- Backend: cloud / local

## Steps to Reproduce (for bugs)
1. ...

## Expected Behaviour
...

## Actual Behaviour
...

## Relevant Logs or Plan Output
```terraform
<paste here>
```
```

### PR vs Issue

| Situation | Use |
|-----------|-----|
| Small, self-contained change | PR only |
| Significant new module or architectural change | Issue first, then PR referencing it |
| Bug or pipeline failure | Issue to document, then PR to fix |
| Question about a past change | Comment on the relevant PR or open an Issue |
